## フェーズ別詳細

### Now: セキュリティと運用の安定化（進行中）

`v0.2.7` では `init_sql` の実行権限分離や DB ログインの非スーパーユーザー化、UNIX ソケットと設定ディレクトリの保護を実施しました。引き続き 1.0 に向けた基盤強化を進めます。

- **権限・アクセス境界の継続強化**: API・認証・通知・ファイル入力などの境界チェックと認可の一貫性を高めます。
- **ProxySQL 3 ルーティング互換性の検証**: コネクションプールやマルチプレキシング有効時のブランチ切り替えにおける prepared statement・一時テーブル・`SET` セッション変数・接続リセットの挙動を主要ドライバ／ORM で検証し、推奨設定と制約事項を明確化します。
- **ドキュメント・配布導線の整備**: ドキュメントサイトやデモ環境、パッケージ配布導線の参照性・安定性を改善します。

### Next: Branch Fork — 既存ブランチからの分岐（計画中）

現在はベーススナップショットからのみブランチを作成できますが、既存ブランチ（`ready` / `paused`）の現在状態や過去のチェックポイントから直接、独立した子ブランチを作成できるようにします。

- **主な機能**:
  - 親ブランチに影響を与えない独立したデータセット・ポート・DSN を持つ子ブランチの即時作成
  - 親ブランチの一時停止なしでのフォーク、および整合性を重視する `--clean` オプション
  - CLI (`db-branch branch fork`)、REST API (`POST /v1/branches/{name}/fork`)、MCP (`fork_branch`)、Web コンソールからの操作
- **v1 スコープ外**: クラスタ内の別ノードをまたぐクロスノードフォーク、および匿名ユーザーによるフォークは対象外とします。

### Next: Branch Merge — 履歴ライン間の論理マージ（計画中）

`branch restore` によって 1 つのブランチ内で分岐・退避された過去の履歴ラインの変更を、現在稼働中のライブラインへ統合できるようにします。

- **主な機能**:
  - 共通祖先を起点とした 3-way 論理比較（行単位の挿入・更新・削除とスキーマ整合性の検査）
  - 実行前の影響確認ができる Dry-run プレビュー（CLI / API / MCP / Web コンソール）
  - 適用前の自動チェックポイント取得と、失敗時の自動ロールバックによる安全性確保
  - コンフリクト検出時はライブラインを一切変更せずに競合箇所を報告
- **v1 スコープ外**: 異なるブランチ間のマージや、対話的なコンフリクト解決 UI は対象外とします。
- **「ブランチ同士はマージ・リベースしない」方針との関係**: db-branch は使い捨て（disposable）のサンドボックスを前提としており、並行して書き込んだ別々のブランチを Git のようにマージ／リベースすることはできません（[README の Design notes](../README.md#design-notes-and-trade-offs) 参照）。ここで扱うのは、`branch restore` で同じブランチ内に残った過去の履歴ラインを、共通祖先との 3-way 比較で、同じブランチの現在の状態へ取り込む機能に限ります。

### Later: ランタイムモジュール標準化（進行中・先行して着手）

現在コアに組み込まれているデータベースエンジン（MySQL / PostgreSQL）の扱いを標準契約（`RuntimeProvider`）と機能宣言（Capability）へ抽象化します。内部の抽象化（MySQL / PostgreSQL を標準契約に適合させる第 1 段階）は実装を終えてレビュー中で、CLI の出力・接続文字列・クラスタの永続化形式は変えていません。続く段階（ユースケース層とインフラ層のエンジン固定部分の置き換え）も進めており、外部モジュールの受け入れ（署名検証・分離境界・Capability の公開）は他の項目の後に行います。MySQL / PostgreSQL は引き続きコアに同梱します。

- **主な機能**:
  - エンジンごとの対応機能（チェックポイント、アップグレード、SQL 実行、ルーティングなど）を明示的に宣言し、非対応操作を安全に案内・拒否する仕組み
  - 外部ランタイムモジュールを署名検証とエンジン別の非特権 OS ユーザー境界のもとで実行するプラグイン基盤
  - ランタイムモジュール向けの適合性検証ツール（Conformance Test）
- **期待される効果**: コアの安定性を損なうことなく、新しいデータベースエンジンを独立したモジュールとして追加・更新できるようになります。

### Later: ClickHouse ランタイム対応（MVP）（検討中）

ランタイムモジュール標準化の基盤を活用し、分析系データベースである ClickHouse に対応します。ClickHouse はデータパーツが不変（immutable）であるため ZFS のブロックレベル CoW クローンと相性が良く、大容量の分析用テスト環境を瞬時に複製できる可能性を見込んでいます。

- **調査・PoC からの段階的アプローチ**: まず典型的なデータセット構成・ポートと設定ファイルの分離・スナップショット取得時のクリーンな停止と復元フローの PoC 検証を行い、対応可否と実装方針を固めます。
- **MVP の想定範囲**:
  - 単一ノードの `MergeTree` テーブルおよびローカル ZFS ストレージを対象としたブランチ作成・リセット・削除・チェックポイント
  - HTTP インターフェース経由での SQL 実行（Web コンソール / MCP）
- **MVP 対象外**: 分散テーブル・ZooKeeper / ClickHouse Keeper とのクラスタ連携、データマスキング、ProxySQL ルーティング、バージョンアップグレードは MVP では非対象とし、ステートフルサービス全般への展開とあわせて 1.0 以降の拡張として検討します。

### Later: 1.0 GA リリース準備・リソース制御強化（検討中）

Beta ステータスを卒業し、ユーザーが長期運用・大規模 AI エージェント／CI 並列実行を前提に採用できる品質基準を満たすフェーズです。

- **ブランチごとの ZFS quota / 自動クリーンアップ強化**: 現行の `--ttl` による期限切れ削除に加え、ブランチ作成時の ZFS quota（`refquota`）上限設定による暴走書き込みのファイルシステム層での制限、および一定時間アイドル状態が続いたブランチの自動破棄またはクリーンなスナップショットへの自動リセット（GC）機構を検討・整備します。
- **PostgreSQL メジャーバージョンアップグレード（`pg_upgrade`）の位置づけ明確化**: 現行（`v0.2.x`）の `branch upgrade` は MySQL のメジャー／シリーズ移行（`5.6 → 5.7 → 8.0 → 8.4 → 9.x`）に対応していますが、PostgreSQL は同一メジャー内のマイナー更新のみ対応しており、`pg_upgrade` を伴うメジャーアップグレードは**未対応**です。`pg_upgrade` 実行・extensions 互換性事前チェック・失敗時自動ロールバックを含む公式サポートの可否と開発優先度（1.0 対象とするか 1.1 以降とするか）を設計調査の上で明確化します。

## 1.0 (GA) の定義（案）

`v1.0.0` のリリースにあたり、以下の条件をすべて満たすことを目標としています（詳細はフィードバックを踏まえて確定します）。

1. **API・CLI の安定化**:
   - REST API (`/v1/...`) および OpenAPI 仕様の破壊的変更を行わない契約の確立（Semantic Versioning の厳格適用）。
   - CLI のサブコマンド体系・終了コード・JSON 出力形式の固定。
2. **互換性保証**:
   - クラスタ間のローリングアップグレードにおける Raft プロトコルおよび状態データの後方互換性保証。
   - 外部モジュール拡張ポイント (`pkg/ext`) の安定化。
3. **セキュリティと多層防御**:
   - DB インスタンス間・ノード間通信の保護、リソース上限（クォータ・TTL 上限等）の整備、監査ログの網羅性確保。
4. **パッケージングと運用性**:
   - サポート対象 OS（Ubuntu LTS）への `apt install db-branch` によるクリーンな導入・アップグレード・アンインストール検証。
   - 監視メトリクス、バックアップ/リストア、障害復旧手順の整備。
5. **ドキュメントの網羅**:
   - 公開ドキュメント（英語・日本語）と OpenAPI リファレンスが 1.0 の全機能・設定・運用手順と一致していること。
