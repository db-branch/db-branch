# ベースを本番から定期的に更新する

ベースを、本番（ソース）のデータベースから決まった間隔で読み直します。手でダンプを読み込んでスナップショットを撮る作業を、スケジュールにしたものです。既存のスナップショットとブランチには触りません。新しいブランチだけが、更新後のデータから作られます。

```
# パスワードは標準入力か環境変数で渡す（引数には出さない）
echo "$SOURCE_PASSWORD" | db-branch base refresh set prod \
    --host db.internal --port 5432 --user dumper --databases app,billing --every 24h --password-stdin

db-branch base refresh show prod      # 設定、最後の実行の結果、次の実行
db-branch base refresh run prod       # 今すぐ更新する
db-branch base refresh off prod       # 定期更新をやめる（接続先とパスワードを忘れる）
```

## 流れ

1. ベースのランタイムに入っているクライアント（PostgreSQL は `pg_dump`、MySQL は `mysqldump`）で、ソースの指定したデータベースをダンプする。
2. ベースを `maintenance` にして、ダンプを読み込む（`base load` と同じ経路）。ダンプには `DROP DATABASE` / `DROP ... IF EXISTS` を含むので、ベースの中身は入れ替わる。
3. ダンプを消す。
4. スナップショットを撮る（`base snapshot` と同じ）。
5. 設定 `base.prune_snapshots` が有効なら、古い未使用のスナップショットを消す。

ベースを持つノードが実行します（30 秒ごとに期限を調べる）。実行は `base.refresh` というオペレーションで、イベントにも出ます。1 つのベースで同時に走るのは 1 回だけです。失敗したときは理由を記録し、次の間隔に再試行します。

読み込みの途中で失敗すると、ベースのサーバーには中途半端なデータが残ります。スナップショットは撮らないので、既存のブランチと新しいブランチの元（最新のスナップショット）は変わりません。次の実行で入れ替わります。

## 設定

| 項目 | 内容 |
|---|---|
| ソース | ホスト、ポート、ユーザー、パスワード、コピーするデータベース（20 個まで）。種類はベースのランタイムのエンジンと同じ |
| 間隔 | `--every`。1 時間以上の期間（`24h` など） |

- PostgreSQL では、データベースごとに `pg_dump --create --clean --if-exists --no-owner --no-privileges` で書く。`postgres` データベースだけは `--create` を付けず、中身を入れ替える。`pg_dump` はソースと同じかそれより新しいメジャー版が必要（ベースのランタイムを合わせる）
- MySQL では `mysqldump --single-transaction --routines --triggers --events --add-drop-database --databases ...` を 1 回実行する
- ソースのユーザーは、読み取りだけできれば足りる

## 本番データの扱い

- ダンプには本番データ（未マスクの場合を含む）が入るため、作業ディレクトリ `<data_dir>/refresh`（`/var/lib/db-branch/refresh`）に `0600` で書き、読み込んだ直後（失敗したときも）に消します。エージェント起動時に前回のクラッシュ等で残った作業ファイルも掃除します。ディスクの空きが 1 GiB 未満になる場合や、設定 `base.refresh_max_gb`（既定 `0` = 無制限）を超える場合はダンプを中止して削除します（[resource-limits.md](resource-limits.md)）
- 外部ランタイムモジュール（専用の OS ユーザー `db-branch-rt-<engine>` で動作）では、ダンプは `<data_dir>/refresh`（`0711`）配下のモジュール所有 `0700` ディレクトリに書き出され、読み込みでもそのまま使われます（コピーしません）。モジュール所有でないダンプ（アップロードしたファイル）だけは、読み込み中、インスタンスの状態ディレクトリ（`<data_dir>/instances/<id>`）へモジュール所有の `0600` で一時コピーし、完了またはエラー時に削除します。その間はダンプサイズの最大 2 倍のディスク空き容量が必要です
- パスワードは環境変数（`PGPASSWORD` / `MYSQL_PWD`）でツールに渡します。コマンドラインにも、ログにも、オペレーションの出力にも出ません。エラーに含まれていた場合は `***` に置き換えます
- パスワードは、クラスタの状態（Raft のログとスナップショット、単一ノードでは `state.json`）に平文で保存されます。ブランチのパスワードと同じ扱いです。API は返さず、`password_set` だけを返します
- 機密データを含む環境では、事前にマスク済みのソースから取り込むか、マスク済みのダンプでベースを作成してください

## 認可

action は `base.refresh.read`（設定を読む）と `base.refresh`（設定、削除、今すぐ実行）です。`base.` で始まるので、既存のロールの規則（メンテナがベースを管理する）がそのまま当てはまります。`branches` スコープのトークンは、どちらも使えません。

## クラスタ

定期更新の設定は、ベースとは別の Raft コマンド（`set_base_refresh`、`record_base_refresh_run`、`clear_base_refresh`、プロトコル 11）で保存します。全ノードが新しい版になるまでは、設定できません。ベースを消すと、設定も消えます。
