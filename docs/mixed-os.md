# ディストリビューションが混在するクラスタ

クラスタのノードは同じディストリビューションでなくてもよい（例: 既存の 3 台が Ubuntu 24.04、4 台目が 26.04）。ただし PostgreSQL のデータは OS の照合順序ライブラリに依存するため、置ける場所に制限がある。

## ノードが報告する情報

各ノードはハートビート（既存の `put_node`）に次を載せる。新しい Raft コマンドは使わず、`Protocol` も上げていない。古いノードは知らないフィールドを読み飛ばし、報告しない項目は `unknown` と表示される。

| 項目 | 内容 | 取得元 |
|---|---|---|
| `distro` | ディストリビューションのキー（`ubuntu-26.04`）。ランタイムの成果物の選択にも使うのと同じ値 | `/etc/os-release` の `ID` と `VERSION_ID` |
| `os` | 表示名（`Ubuntu 26.04.1 LTS`） | `PRETTY_NAME` |
| `kernel` | 動作中のカーネル | `/proc/sys/kernel/osrelease`（`uname -r`） |
| `zfs` | ZFS の版。カーネルモジュールの版が違えば `2.3.1-1 (kmod 2.2.2-0ubuntu9)` | `zfs version`（`zfs-` と `zfs-kmod-` の行） |

取得結果は 1 時間キャッシュする（再起動やパッケージ更新がなければ変わらず、ハートビートは数秒おきのため）。`GET /v1/cluster`、`db-branch cluster status`（OS 列）、コンソールの Cluster ページに出る。

ディストリビューションが違うと `db-branch` ユーザーの uid/gid も違いやすい（24.04 と 26.04 など）。ベースのコピーは数値の所有者のまま運ばれるので、クラスタ全体で揃える。参加時の付け替えと食い違いの扱いは [service-user-ids.md](service-user-ids.md)。

## なぜ PostgreSQL だけか

PostgreSQL は文字列の並び順を glibc のロケールデータ（または ICU）で決め、B-tree インデックスはその順序で作られる。別のリリースのノードでデータディレクトリを開くと、ロケールデータが違えばインデックスが壊れたように見え（検索漏れ、一意制約の破れ）、`collation version mismatch` の警告も出る。

MySQL は照合順序の実装（`utf8mb4_0900_ai_ci` など）と文字セットのデータをサーバー自身に持つ。ここで使うのは上流の汎用 Linux 配布のバイナリで、システムのロケールや ICU には依存せず、`internal/infrastructure/mysql` の `Fixup` が補うのも `libaio` の別名だけである。このため OS が違っても影響しないと判断し、MySQL には何の制限も付けていない（コードを読んだ範囲での判断で、実機での照合順序の比較まではしていない）。

## 規則

対象は PostgreSQL のランタイムのベースだけ（`domain.CollationBound`）。

- **記録**: ベースのスナップショットを作る（作成・更新・マスクの結果）とき、そのノードの `distro` をスナップショットに記録する（`BaseSnapshot.distro`）。記録のない既存のスナップショットは、ベースの担当ノードがいま報告している `distro` を元とみなす。
- **自動配置**: 新しいブランチは、元の `distro` と同じノードにだけ置く。該当するノードが残らなければ 409 で断る。
- **明示指定**: `--node`（API の `node`）で別の `distro` のノードを選ぶと 409。理由（照合順序ライブラリの違い）を応答に含める。
- **レプリカ**: PostgreSQL のベースの `replica_nodes` に別の `distro` のノードを入れると 409。`replica_nodes` を指定しない（全ノード）場合でも、別の `distro` のノードはコピーを受け取らない（使えないコピーに帯域を使わないため）。
- **表示**: 別の `distro` のためコピーを受け取らないノードは、`db-branch base show` の `Holder:` に `skipped (other OS: ubuntu-26.04)`（括弧内はそのノードの `distro`）と出る。`pulling` とは別の状態で、取得は始まらない。API のベースの `holders` では `state: "skipped"` で、`reason`（`other OS: ubuntu-26.04`）と `distro` が付く（どちらも追加のフィールド）。コンソールの Replicas カードは灰色で理由を添え、ベース一覧のノードの印は破線の薄い表示になる。`dbbranch_base_replicas_missing`（複製の遅れ）にはこのノードと、`replica_nodes` に含まれないノードは数えない。コピーをすでに持っているノードは、そのまま `held` と表示する。
- **ノード喪失後の作り直し**: `recreate` も同じ規則で配置する。同じ `distro` のコピーを持つノードがなければ作り直せない。
- **不明は妨げない**: `distro` を報告しないノード（古いバージョン、`/etc/os-release` が読めない）は、違うと示せないため除外しない。ローリングアップグレード中に配置が止まらないための選択である。

これらは Raft の状態にフィールドを足しただけで（`put_base` の中の `distro`、`put_node` の中の `system`）、新しいコマンドも `Protocol` の変更もない。古いノードが書いた `put_base` はこのフィールドを落とすことがあり、そのときは上の「記録のない既存のスナップショット」の扱いに戻る。

## 回避策

別のディストリビューションのノードで PostgreSQL のブランチが必要なら、そのノードでベースを作り直す（ダンプから読み込む）。ベースはそのノードの `distro` で記録され、同じ `distro` のノードにブランチを置ける。

## 既知の制限

- 同じ `distro` の中でも glibc や ICU の更新で照合順序が変わることがある（`apt upgrade`）。これは検出しない。
- `base mask` の作業用サーバーは、ソースのスナップショットのコピーが必要なので、別の `distro` のノードにはコピーがなく、実行できない（「まだレプリケートされていません」の 409）。
