# チェックポイント（ブランチの途中経過の保存と復元）

稼働中のブランチの状態を名前を付けて保存し（チェックポイント）、あとでその状態に戻せる。危ないマイグレーションや一括更新の前に取り、失敗したら戻す使い方を想定している。LLM エージェントも MCP から同じことができる。

名前は **Checkpoint**（ベースの `Snapshot` とは別物。コンソールでも英語のまま）。

## 1. 何ができるか

| 操作 | CLI | API | MCP |
|---|---|---|---|
| 保存 | `branch checkpoint <ブランチ> [--name x]` | `POST /v1/branches/{name}/checkpoints` | `create_checkpoint` |
| 一覧 | `branch checkpoints <ブランチ>` | `GET /v1/branches/{name}/checkpoints` | `list_checkpoints` |
| 復元 | `branch restore <ブランチ> <チェックポイント>` | `POST /v1/branches/{name}/checkpoints/{checkpoint}/restore` | `restore_checkpoint` |
| 削除 | `branch checkpoint delete <ブランチ> <チェックポイント>` | `DELETE /v1/branches/{name}/checkpoints/{checkpoint}` | （なし） |

- 保存は一瞬（ZFS のスナップショット）で、DB サーバーは止めない。名前を省くと UTC の時刻（`20261112-153000`）になる
- 一覧は名前・作成時刻・容量（そのチェックポイントだけが持つ容量）・属する線・自動かどうか・「現在のデータの元になったもの」の印を返す
- **復元すると、いまの状態は置き換わる。自動では保存しない**。残したいときは、復元の前に Checkpoint を取る（コンソールの確認ダイアログには「Save a checkpoint first」のボタンがあり、CLI は開始前に注意を 1 行出す）。すでにあるほかの Checkpoint は、すべて残り、どれも何度でも復元できる。以前の版が復元の前に自動で取った `before-restore-<時刻>` は、そのまま残り、ほかのものと同じように復元も削除もできる
- Checkpoint は取ったときの**ランタイム**（`mysql@8.0.46` など）を記録する。復元するとブランチはそのランタイムに戻る（[upgrade.md](upgrade.md)）。アップグレードの前には、自動の Checkpoint `before-upgrade-<時刻>` が取られる（新しい 5 件を残し、`branch.max_checkpoints` に数えない）。リセットは Base の状態と Base のランタイムに戻す
- ブランチを削除すると、そのブランチのチェックポイントも全部消える
- 一覧は Raft に置かない。ZFS（スナップショットのユーザープロパティ）から担当ノードが読み、API はどのノードに来ても担当ノードへ転送する。Raft のコマンドもプロトコルも変えていない

## 2. 整合性：クラッシュコンシステント

DB のデータディレクトリと WAL / redo ログは同じデータセットにある（PostgreSQL は `PGDATA` の中の `pg_wal`、MySQL は `datadir` の中の redo ログ）。そのため、稼働中のデータセットのスナップショットは「その瞬間に電源が落ちた」状態と同じで、DB はそこから起動して自力で回復する。サーバーを止める必要はない。

ベースのスナップショットは、止めてから取る（クリーンシャットダウン）のに対し、チェックポイントはクラッシュコンシステントである。復元の前の自動チェックポイントだけは、サーバーを止めてから取る（クリーンシャットダウンできなければ即時停止にフォールバックする）。

## 3. データセットの配置

ブランチ `x` のデータセットは、既存のブランチと同じ場所のまま：

```
<pool>/db-branch/branches/x            ライブのデータセット（DB サーバーのデータディレクトリ。パス・ポート・systemd ユニットは変わらない）
<pool>/db-branch/history/x             退避した線の入れ物（マウントしない。復元の記録もここに持つ）
<pool>/db-branch/history/x/<n>         復元で退避した線（チェックポイントを残すため。マウントしない）
<pool>/db-branch/history/x/new         復元で差し替える途中のクローン（マウントしない）
```

- `branches/` の直下は今までどおりブランチだけなので、ブランチの列挙・使用量・Adopt・Reconcile の挙動は変わらない
- **既存のブランチは移行なしでそのまま動く**。チェックポイントを一度も取っていなければ `history/` は存在せず、リセットも今までどおり `zfs rollback` で行う
- チェックポイントは `branches/x@ckpt-<名前>` というスナップショットで、ユーザープロパティ `db-branch:line`（属する線）と `db-branch:auto`（自動かどうか）を持つ。ライブのデータセットのプロパティ `db-branch:head` が「現在のデータの元になったチェックポイント」を指す
- 容量は、ライブ + `history/x` 以下の使用量を合わせて、ブランチの Storage 表示（API の `storage`、クラスタ内の他ノードの表示も）に数える

## 4. 復元の手順

`x` を `c1` に戻す。ライブを `L`、チェックポイントが載っているデータセットを `S` とする。

1. `history/x` に**意図**を書く（`db-branch:op=restore`、元のスナップショット名、新しい線の番号、自動チェックポイントの名前）。ブランチの状態を `restoring` にする
2. `S@ckpt-c1` を `history/x/new` へクローンする（マウントしない。サーバーはまだ動いている）
3. サーバーを止める（クリーン、だめなら即時）
4. `L` のマウントを外し（`canmount=off`）、`history/x/<Lの線の番号>` へリネームする
5. `history/x/new` を `branches/x` へリネームし、`canmount=on` にしてマウントする
6. `zfs promote branches/x` を、元が自分の線のものである間だけ繰り返す。これで新しいライブが履歴のスナップショット（`reset` を含む）をすべて持ち、退避した線はライブのクローンになる。**ベースのスナップショットから切るクローンの関係は絶対に昇格しない**（ベースがブランチのクローンになってしまうため）
7. サーバーを起動し、意図を消し、チェックポイントの無くなった線を捨てる。状態を `ready` にする

操作は `branch.restore` のオペレーションで、イベントは `branch.reset` と同じように流れる。進捗は `cloning` `stopping` `checkpointing` `swapping` `promoting` `starting`。

### クラッシュしても必ず終わる

各ステップは、始める前にディスクの状態（クローンがあるか、ライブの線の番号が新しい番号か、自動チェックポイントがあるか、昇格済みか）を見て、済んでいれば飛ばす。意図は ZFS のプロパティなので、エージェントが落ちても残る。

- ステップ 4 と 5 の間だけ `branches/x` が存在しない。再開は必ず前に進み、`history/x/new` を `branches/x` にする。データディレクトリが無いまま放置されることはない
- 起動時の `Recover` が、状態が `restoring` のブランチ（と、復元の途中で失敗して `failed` になったブランチ）の意図を読んで続きを実行する。意図が書かれる前に落ちたなら何も変わっていないので、そのまま起動する
- 結果は「元の状態のまま」か「復元済み」のどちらかで、その中間にならない。テストは、復元のすべての副作用（ZFS 操作・サーバー操作・状態の更新）の直前でエージェントを落とし、再起動後の状態を確かめている（二重にクラッシュする場合も）
- 手順の途中で（クラッシュではなく）失敗した場合、リネームの前なら元に戻す（クローンを捨て、自動チェックポイントを消し、サーバーを起動して `ready` に戻す）。リネームの後なら `failed` にし、意図を残して、次の起動で完了させる

## 5. リセットとの関係

`branch reset` は「作成時の状態に戻す」意味のまま、**チェックポイントを残す**。

- ライブのデータセットにスナップショットが `reset` だけなら、今までどおり `zfs rollback`
- チェックポイントがあるときは `zfs rollback` だと新しいスナップショットが消えてしまうので、同じ入れ替えの手順で、`reset` スナップショットのクローンをライブにする。リセットで捨てる状態はチェックポイントとして残さない（リセットは「捨てる」操作）。現在地の印は消える
- `reset` スナップショットは昇格によってライブに移るので、どれだけ復元を重ねてもリセットできる

## 6. 削除と後始末

- **チェックポイントの削除**：スナップショットを消す。復元で作った線がそのスナップショットからのクローンのときは消せないので、`gone-<時刻>` という名前に替えて見えなくし、クローンが無くなったときに消す
- **線の自動削除（GC）**：ライブでなく、チェックポイントも `reset` もクローンの元も持たない線のデータセットは、チェックポイントの削除・復元の完了のたびに自動で破棄する。入れ物が空になれば入れ物も破棄する
- **ブランチの削除**：ライブ・退避した線・途中のクローンを、**クローンの側から順に 1 つずつ** `zfs destroy -r` で消し、最後に入れ物を消す。`zfs destroy -R` は使わない。消す前に全データセットのスナップショットのクローンを調べ、このブランチの外にクローンがあれば何も消さずに失敗する（`in_use`）。ほかのブランチやベースに触れないことはテストで確かめている
- ノードが失われて別ノードで作り直した（`recreate`）ブランチは、ベースから作り直すのでチェックポイントを引き継がない

## 7. 上限

設定 `branch.max_checkpoints`（Settings の「Checkpoints per branch」、既定 20、`core`）。1 つのブランチに**自分で保存できる**チェックポイントの数（全ての線の合計）。超える保存は `409 conflict`。0 にするとチェックポイントを作れない。

自動で取る Checkpoint（アップグレードの前の `before-upgrade-<時刻>`、以前の版が復元の前に取った `before-restore-<時刻>`）は、この上限に**数えない**。上限が理由で復元が断られることもない。代わりに自動のものは**新しい 5 件だけ**残す。アップグレードで 6 件目ができると、一番古い自動チェックポイントを、通常のチェックポイント削除と同じ手順（依存する線の扱いと GC を含む）で消す。消せなかったときはアップグレードは成功のままで、ログに残し、次のときにもう一度試す。手動のチェックポイントは回転の対象にならない。復元は、自動のチェックポイントを取らない。

保存の応答には、そのブランチの使用量（ライブ + 履歴）がプールの空きの半分を超えたときに限り、`warning`（文字列）が付く。断りはしない。コンソールは保存の下に、CLI は標準エラーに出す。空きが分からないノードでは付かない。

各チェックポイントは、守っているデータの分だけ容量を使う。不要になったら削除する。

## 8. 権限

操作は `branch.checkpoint.read`（一覧）、`branch.checkpoint`（保存）、`branch.restore`（復元）、`branch.checkpoint_delete`（削除）。ほかのブランチ操作と同じく、所有者と管理者（と `branches` スコープのトークン）が使える。**ログインなしの呼び出しや、`open` のブランチは、チェックポイントの操作を許さない**（`open` は接続を許すだけで、履歴を変える権限ではない）。有償の認証モジュールのロールがこれらを使うには、アクション名の対応を足す。

## 9. 制限

- ノード自身の ZFS で動くブランチだけが対象。モジュールのストレージ（共有ストレージなど）では `409`（エラーコード `checkpoints_unavailable`、`checkpoints are not available on this storage ...`）。ブランチの JSON の `checkpoints` が `false` になり、コンソールはチェックポイントの欄と操作を出さず、CLI は一行で伝え、MCP はこのエラーを返す
- チェックポイントはクラッシュコンシステント。アプリケーションの整合性（複数テーブルをまたぐ処理の途中など）を保証するものではないが、DB の通常のクラッシュ回復と同じ範囲に収まる
- 復元の間（MySQL で約 2 秒、PostgreSQL で約 0.7 秒）はブランチに接続できない

## 10. 履歴のグラフと、有償の history モジュール

- 一覧 API（`GET /v1/branches/{name}/checkpoints`）は、チェックポイントに加えて線の構造（`lines`・`live`・`head`）を返す。コンソールは Branches の各ブランチの Checkpoints に、線をレーン、チェックポイントを節、復元を元のチェックポイントからの枝として描く（キーボードでも選べる）。ここからチェックポイントを復元できる。無償
- 線の親と元のチェックポイントは、復元で作る線のデータセットのプロパティ `db-branch:from` と `db-branch:parent` に持つ。この版より前に作った線は元が分からない（親なしの線として描く）
- 有償の `history` モジュールを入れると、ブランチの変更を記録して**チェックポイントの間の任意の時点**へ戻せ、グラフに記録したトランザクションが点で並ぶ。拡張点は `docs/modules.md`、使い方は `db-branch-modules` の `docs/history.md`
- **記録するかどうかは、ブランチを作るときに一度だけ決まり、あとから変えられない**（作成時に `record: true` を付けるか、そのときモジュールの `record_all` がオンか）。途中でオンやオフにするとログに抜けができて、その区間へは戻せなくなるので、切り替える手段を用意しない。記録するブランチは、作成・作り直し・リセット・復元・再起動のどれでも、モジュールが無いか止まっているかライセンスが無いと起動しない（理由は `status_reason`）。記録しないブランチは、あとから `record_all` をオンにしても記録しない。コンソールとCLI（`branch show`）、API（`record`）は「Recording: on（作成時から）／off」を表示するだけで、チェックボックスは作成画面にしかない

### コンソールのグラフの描き方

表示だけの規則で、API・Raft の状態・サーバーの動きは変わらない。

- **Expand ボタン**：グラフの上の「Expand」で、Checkpoints の欄ぜんぶ（グラフ・選んだ節の詳細と操作・保存の名前欄・一覧・確認・エラーや状態の表示）をモーダルに大きく開く。ページの欄とモーダルは同じ状態を描くので、選択も、操作後の更新も共通。閉じても選択は残る。Esc・Close・外側のクリックで閉じ、閉じたあとは Expand ボタンにフォーカスが戻る。Checkpoint が 1 つもないときはボタンを出さない
- **チェックポイントがなくても、記録したトランザクションがあれば描く**：履歴を記録するブランチは、リセットの直後など、チェックポイントも線の分かれもない状態でも、トランザクションが1件でもあれば、グラフを出す（作成時の状態から点が並ぶ）。点が1つもない間は、「No checkpoints yet.」だけを出す
- **続けて行われたトランザクションは1つの点にまとめる**：同じ線で、前のトランザクションから1秒未満で続いたものは、1つの点（件数「×3」付き、aria-label は「3 transactions, #1 to #3」）にする。1回の保存で数行を追加したときなどが、これにあたる。DDL は単独の点のままで、グループを区切る。その線のチェックポイントの時刻をまたぐグループも作らない。グループを選ぶと、詳細に、トランザクションを時刻順の表（#・時刻・行数・文）で出す。行を選ぶと（最初に選ばれているのは最後の行）、その下に「Restore to #N」のボタンだけが出る（文や行数は表にあるので、繰り返さない）。復元は行ごとで、グループ全体を1つの復元先にはしない。区間（隣り合う節の間）が狭くて点が収まらないときは、時刻がいちばん近い隣同士から、1つのグループにまとめていき（DDL はまとめない）、点は最低 14px、グループは 26px の場所を取る。まとめても、トランザクションは1件も落とさず、グループを選べば表で全件見られる（点を間引いて見えなくすることはしない）。それでも収まらないときだけ、詰めて並べる。表示だけの規則で、API は変わらない
- **横の位置**：1本のレーンの中では、左から右へ時刻順に並ぶ。分岐したレーンは、ほかのレーンとの時刻の前後は気にせず、分岐元のノードのすぐ右（24px）から始まり、そのレーン自身のチェックポイントが、1つずつ右へ並ぶ（時間が空いても、右へ離れない）。表示の幅は、いちばん右のレーンに合わせる
- **復元の枝**：中ほどの復元の枝は、元の線から、急な角度（ほぼ直角）で次のレーンへ下り（上り）、そのあとレーンに沿って、まっすぐ破線で続く（曲線は使わない）
- **先端の復元は線を延ばす**：復元は新しい線を作るが、復元したのが**その線の先端**なら、新しいレーンは作らず、同じレーンが右へ延びる（枝の曲線も「line N」の名前もなく、色も同じ）。何も取り残さないため。中ほどの復元は今までどおり新しいレーンに枝分かれする
- 先端とみなす条件（すべて満たすとき）：
  1. 線の元が分かっている（`parent` が null でなく、`from` が `reset` か、その線に今もあるチェックポイント）
  2. 元の点より後ろの節が、そのレーンにない。レーンは、そこに描いてある線のうち、新しい線より番号の小さいもの。後ろの節は、チェックポイント（作成時刻、同時刻なら名前の順）と記録したトランザクション（時刻）。ただし自動の `before-restore-*` は数えない（以前の版の復元が、離れる線の復元した点のすぐ後に必ず取った控えで、線の進みではないため。いまの版の復元は取らない）。手で付けた名前が `before-restore-` で始まるものや `before-upgrade-*` は数える。作成時の状態（`reset`）が先端なのは、チェックポイントもトランザクションもないレーンだけ
  3. 記録するブランチ（`record`）では、そのレーンのすべての線のトランザクションが読めている。読めない（history の権限がない、読み込みに失敗した）ときは先端かどうか分からないので、今までどおり枝分かれさせる
- 延びたレーンの上のノードは、レーンの線の番号で呼ぶ（`aria-label` の「line 0」、詳細、一覧の「line」）。APIの線の番号は変えず、トランザクションからの復元などAPIへは本来の番号を渡す。レーンの名前は最初に描いた線の番号のまま、振り直さない（line 0 の隣が line 3 になることがある）。レーンが 1 本だけのとき、一覧に線の番号は出さない
- 連続して先端を復元すると、そのたびに同じレーンが延びる。復元の前の自動チェックポイントはレーンに並ぶが、データの元ではない（`head` の輪は、データの元のチェックポイントに付いたまま。右端の「now」の矢印はレーンの端）
- **トランザクションへの復元**（history モジュール）：コアの API は、その線を「直前のチェックポイントからの復元」としか返さない。history モジュールは、復元して再生したあと、戻したトランザクションを覚えていて、イベントの応答（`GET /v1/ext/history/branches/{name}/events?line=`）の `from_tx`（GTID）でそれを返す。その線のログにそのトランザクションがあるときだけ付く。コンソールは、`from_tx` を復元した点とみなし、その点より後ろの節（元のレーンのチェックポイントとトランザクション）がなければ先端として、同じレーンを延ばす。後ろに残るものがあれば、今までどおり枝分かれする。`from_tx` がない（チェックポイントへの復元、古いモジュール、覚えていない）ときは、直前のチェックポイントからの復元として扱う
- 限界（API が教えないこと）：復元した時刻と、復元の前に先端から状態が変わっていたか。自動のチェックポイントを取らないので、復元で離れた線の、最後のチェックポイントより後のトランザクションは、その線のログから読めなくなる（戻したところまでは、新しい線が再生して持つ）
