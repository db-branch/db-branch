# チェックポイント（ブランチの途中経過の保存と復元）

稼働中のブランチの状態を名前を付けて保存し（チェックポイント）、あとでその状態に戻せる。危ないマイグレーションや一括更新の前に取り、失敗したら戻す使い方を想定している。LLM エージェントも MCP から同じことができる。

名前は **Checkpoint**（ベースの `Snapshot` とは別物。コンソールでも英語のまま）。

## 1. 何ができるか

| 操作 | CLI | API | MCP |
|---|---|---|---|
| 保存 | `branch checkpoint <ブランチ> [--name x]` | `POST /v1/branches/{name}/checkpoints` | `create_checkpoint` |
| 一覧 | `branch checkpoints <ブランチ>` | `GET /v1/branches/{name}/checkpoints` | `list_checkpoints` |
| 復元 | `branch restore <ブランチ> <チェックポイント>` | `POST /v1/branches/{name}/checkpoints/{checkpoint}/restore` | `restore_checkpoint` |
| 削除 | `branch checkpoint delete <ブランチ> <チェックポイント>` | `DELETE /v1/branches/{name}/checkpoints/{checkpoint}` | （なし） |

- 保存は一瞬（ZFS のスナップショット）で、DB サーバーは止めない。名前を省くと UTC の時刻（`20261112-153000`）になる
- 一覧は名前・作成時刻・容量（そのチェックポイントだけが持つ容量）・属する線・自動かどうか・「現在のデータの元になったもの」の印を返す
- **復元しても何も失われない**。復元の前に今の状態を `before-restore-<時刻>` として自動で保存し、ほかのチェックポイントもすべて残る。どのチェックポイントも何度でも復元できる
- ブランチを削除すると、そのブランチのチェックポイントも全部消える
- 一覧は Raft に置かない。ZFS（スナップショットのユーザープロパティ）から担当ノードが読み、API はどのノードに来ても担当ノードへ転送する。Raft のコマンドもプロトコルも変えていない

## 2. 整合性：クラッシュコンシステント

DB のデータディレクトリと WAL / redo ログは同じデータセットにある（PostgreSQL は `PGDATA` の中の `pg_wal`、MySQL は `datadir` の中の redo ログ）。そのため、稼働中のデータセットのスナップショットは「その瞬間に電源が落ちた」状態と同じで、DB はそこから起動して自力で回復する。サーバーを止める必要はない。

ベースのスナップショットは、止めてから取る（クリーンシャットダウン）のに対し、チェックポイントはクラッシュコンシステントである。復元の前の自動チェックポイントだけは、サーバーを止めてから取る（クリーンシャットダウンできなければ即時停止にフォールバックする）。

## 3. データセットの配置

ブランチ `x` のデータセットは、既存のブランチと同じ場所のまま：

```
<pool>/db-branch/branches/x            ライブのデータセット（DB サーバーのデータディレクトリ。パス・ポート・systemd ユニットは変わらない）
<pool>/db-branch/history/x             退避した線の入れ物（マウントしない。復元の記録もここに持つ）
<pool>/db-branch/history/x/<n>         復元で退避した線（チェックポイントを残すため。マウントしない）
<pool>/db-branch/history/x/new         復元で差し替える途中のクローン（マウントしない）
```

- `branches/` の直下は今までどおりブランチだけなので、ブランチの列挙・使用量・Adopt・Reconcile の挙動は変わらない
- **既存のブランチは移行なしでそのまま動く**。チェックポイントを一度も取っていなければ `history/` は存在せず、リセットも今までどおり `zfs rollback` で行う
- チェックポイントは `branches/x@ckpt-<名前>` というスナップショットで、ユーザープロパティ `db-branch:line`（属する線）と `db-branch:auto`（自動かどうか）を持つ。ライブのデータセットのプロパティ `db-branch:head` が「現在のデータの元になったチェックポイント」を指す
- 容量は、ライブ + `history/x` 以下の使用量を合わせて、ブランチの Storage 表示（API の `storage`、クラスタ内の他ノードの表示も）に数える

## 4. 復元の手順

`x` を `c1` に戻す。ライブを `L`、チェックポイントが載っているデータセットを `S` とする。

1. `history/x` に**意図**を書く（`db-branch:op=restore`、元のスナップショット名、新しい線の番号、自動チェックポイントの名前）。ブランチの状態を `restoring` にする
2. `S@ckpt-c1` を `history/x/new` へクローンする（マウントしない。サーバーはまだ動いている）
3. サーバーを止める（クリーン、だめなら即時）。`L@ckpt-before-restore-<時刻>` を取る
4. `L` のマウントを外し（`canmount=off`）、`history/x/<Lの線の番号>` へリネームする
5. `history/x/new` を `branches/x` へリネームし、`canmount=on` にしてマウントする
6. `zfs promote branches/x` を、元が自分の線のものである間だけ繰り返す。これで新しいライブが履歴のスナップショット（`reset` を含む）をすべて持ち、退避した線はライブのクローンになる。**ベースのスナップショットから切るクローンの関係は絶対に昇格しない**（ベースがブランチのクローンになってしまうため）
7. サーバーを起動し、意図を消し、チェックポイントの無くなった線を捨てる。状態を `ready` にする

操作は `branch.restore` のオペレーションで、イベントは `branch.reset` と同じように流れる。進捗は `cloning` `stopping` `checkpointing` `swapping` `promoting` `starting`。

### クラッシュしても必ず終わる

各ステップは、始める前にディスクの状態（クローンがあるか、ライブの線の番号が新しい番号か、自動チェックポイントがあるか、昇格済みか）を見て、済んでいれば飛ばす。意図は ZFS のプロパティなので、エージェントが落ちても残る。

- ステップ 4 と 5 の間だけ `branches/x` が存在しない。再開は必ず前に進み、`history/x/new` を `branches/x` にする。データディレクトリが無いまま放置されることはない
- 起動時の `Recover` が、状態が `restoring` のブランチ（と、復元の途中で失敗して `failed` になったブランチ）の意図を読んで続きを実行する。意図が書かれる前に落ちたなら何も変わっていないので、そのまま起動する
- 結果は「元の状態のまま」か「復元済み」のどちらかで、その中間にならない。テストは、復元のすべての副作用（ZFS 操作・サーバー操作・状態の更新）の直前でエージェントを落とし、再起動後の状態を確かめている（二重にクラッシュする場合も）
- 手順の途中で（クラッシュではなく）失敗した場合、リネームの前なら元に戻す（クローンを捨て、自動チェックポイントを消し、サーバーを起動して `ready` に戻す）。リネームの後なら `failed` にし、意図を残して、次の起動で完了させる

## 5. リセットとの関係

`branch reset` は「作成時の状態に戻す」意味のまま、**チェックポイントを残す**。

- ライブのデータセットにスナップショットが `reset` だけなら、今までどおり `zfs rollback`
- チェックポイントがあるときは `zfs rollback` だと新しいスナップショットが消えてしまうので、同じ入れ替えの手順で、`reset` スナップショットのクローンをライブにする。リセットで捨てる状態はチェックポイントとして残さない（リセットは「捨てる」操作）。現在地の印は消える
- `reset` スナップショットは昇格によってライブに移るので、どれだけ復元を重ねてもリセットできる

## 6. 削除と後始末

- **チェックポイントの削除**：スナップショットを消す。復元で作った線がそのスナップショットからのクローンのときは消せないので、`gone-<時刻>` という名前に替えて見えなくし、クローンが無くなったときに消す
- **線の自動削除（GC）**：ライブでなく、チェックポイントも `reset` もクローンの元も持たない線のデータセットは、チェックポイントの削除・復元の完了のたびに自動で破棄する。入れ物が空になれば入れ物も破棄する
- **ブランチの削除**：ライブ・退避した線・途中のクローンを、**クローンの側から順に 1 つずつ** `zfs destroy -r` で消し、最後に入れ物を消す。`zfs destroy -R` は使わない。消す前に全データセットのスナップショットのクローンを調べ、このブランチの外にクローンがあれば何も消さずに失敗する（`in_use`）。ほかのブランチやベースに触れないことはテストで確かめている
- ノードが失われて別ノードで作り直した（`recreate`）ブランチは、ベースから作り直すのでチェックポイントを引き継がない

## 7. 上限

設定 `branch.max_checkpoints`（Settings の「Checkpoints per branch」、既定 20、`core`）。1 つのブランチが持てるチェックポイントの数（全ての線の合計、自動のものを含む）。超える保存は `409 conflict`。復元の前に自動で取る 1 件だけは、上限を 1 つ超えてよい（`数 > 上限` のときは復元を断る）。0 にするとチェックポイントを作れない。

各チェックポイントは、守っているデータの分だけ容量を使う。不要になったら削除する。

## 8. 権限

操作は `branch.checkpoint.read`（一覧）、`branch.checkpoint`（保存）、`branch.restore`（復元）、`branch.checkpoint_delete`（削除）。ほかのブランチ操作と同じく、所有者と管理者（と `branches` スコープのトークン）が使える。**ログインなしの呼び出しや、`open` のブランチは、チェックポイントの操作を許さない**（`open` は接続を許すだけで、履歴を変える権限ではない）。有償の認証モジュールのロールがこれらを使うには、アクション名の対応を足す。

## 9. 制限

- ノード自身の ZFS で動くブランチだけが対象。モジュールのストレージ（共有ストレージなど）では `409`（`checkpoints need this node's own ZFS storage`）
- チェックポイントはクラッシュコンシステント。アプリケーションの整合性（複数テーブルをまたぐ処理の途中など）を保証するものではないが、DB の通常のクラッシュ回復と同じ範囲に収まる
- 復元の間（MySQL で約 2 秒、PostgreSQL で約 0.7 秒）はブランチに接続できない
