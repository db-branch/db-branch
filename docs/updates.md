# マイナー更新（コンソールから）

管理者は、ノードにログインせずに、クラスタの db-branch パッケージを新しいマイナー版・パッチ版へ更新できる。コンソールの Settings → Updates、または `db-branch update` を使う。

## 更新の種類

版は `MAJOR.MINOR.PATCH`（`~dev…` などの接尾辞つき）で、Debian のバージョン順（dpkg と同じ）で比べる。

- **マイナー更新**: 新しく、MAJOR が同じ版。パッチ版も含む。コンソールから適用できる
- **メジャー更新**: MAJOR が上がる版。一覧には出るが、コンソールと API からは適用できない。手順書に従って手作業で行う（下記）
- ダウングレードは扱わない

## 流れ

1. **確認** — 「Check for updates」（`db-branch update check`）。要求を受けたノードが `apt-get update` を db-branch のリポジトリ（`/etc/apt/sources.list.d/db-branch.list`）だけに対して実行し、`db-branch` と入っている `db-branch-*` の候補を `apt-cache` で読む。結果は Raft に記録され、どのノードのコンソールにも出る。ネットワークに出るのはこのときだけ（設定 `update.auto_check` を有効にすると、リーダーが 1 日 1 回確認する。既定はオフ）。パッケージのインストール時には何もしない
2. **適用** — 最新のマイナー版の「Update」を押し、確認画面で開始する（`db-branch update apply <版>`）。コアを指定の版へ、各モジュールを「インストール済みの版と MAJOR が同じ最新版」へ上げる。モジュールの候補がより新しい db-branch を要求するときは、その版を飛ばし、理由を画面に出す
3. **ロールアウト** — ノードは 1 台ずつ更新する。順番は、フォロワーを名前順、リーダー（開始時点）を最後。次のノードは、前のノードが心拍で目標の版を報告し、健全であるときにだけ始まる

## 各ノードで起こること

- そのノードのエージェントが「開始」を Raft に記録してから `apt-get install -y --only-upgrade db-branch=<版> <モジュール=版…>` を実行する。パッケージの postinst が `db-branch.service` を再起動するので、エージェントは自分の再起動を想定内として扱う
- リーダーの番が来ると、先にリーダーを他のノードへ移してから更新する
- 新しい版で起動したノードが心拍で目標の版を報告すると、リーダーが「完了」と記録する
- 1 台 15 分以内に目標の版を報告しなければ失敗とする。次のノードが始められないまま（前のノードが完了後に落ちた、次のノードが落ちている、など）、前のノードの完了から 15 分たったときも、理由を示して失敗とする
- 単一ノード（Raft なし）でも同じ流れで自分自身を更新する

## 更新中の既知の制約

- **混在クラスターでのログアウト失効（プロトコル 24 未満）**: 全ノードがプロトコル 24 以上になるまで、`POST /v1/auth/logout` の失効記録を Raft に書き込めない。更新中のノードでログアウトすると、そのノードはメモリ上でセッションを失効したうえで `503 cluster_upgrading` を返し（「更新完了後にもう一度ログアウト」を案内）、Cookie は消さずに残す。全ノードの更新が完了すると保留分が自動で Raft に書き込まれるが、更新完了前にそのノードが再起動した場合や別ノードに送られた場合は、更新完了後の再ログアウトまたはセッション期限切れまで他ノード・再起動後にセッションが有効のまま残る（管理者のパスワード変更は世代番号を更新するため、この制約を受けず全セッションを即時に無効化する）。

## 再起動で何が止まるか

ノードの更新はサービスの再起動である。ブランチとベースは、通常の `systemctl restart db-branch` のときと同じ範囲でしか動き続けない（エージェントが止まっている間は API とコンソールに繋がらず、起動後に復旧処理でブランチとベースが戻る）。更新は 1 台ずつなので、他のノードのブランチは動き続ける。心配なら更新の前にバックアップを取る。

## 安全のための拒否

次のときは開始できない。

- どれかのノードが落ちている、または心拍が届かない
- すでにロールアウトが走っている
- どれかのノードにとって、目標がマイナー更新でない（古い版、メジャー更新）。すでに目標の版のノードは飛ばす
- クラスタに古いプロトコルのノードがいる（全ノードを新しい版にするまでロールアウトの記録は書けない）

## 失敗したとき

- どれかのノードで apt が失敗する、または時間内に新しい版にならないと、ロールアウトはそこで止まり、画面に理由が出る。自動では元に戻さない
- ノードで原因（ディスク、リポジトリ、dpkg の状態）を直し、「Check for updates」のあとにもう一度適用する。更新済みのノードは飛ばして続ける
- 実行中のロールアウトは「Stop the rollout」（`db-branch update cancel`）で止められる。まだ始まっていないノードは更新されない。更新中のノードはそのまま終わる

## 手作業での更新（`apt upgrade`・メジャー更新）

コンソールを使わず `apt upgrade` や `apt-get install` で更新するとき（メジャー更新、またはパッチ版を手動で当てるとき）は、次の順で行う。

1. リリースノートと互換性を確認し、バックアップを取る（`db-branch backup`）
2. ノードを 1 台ずつ更新する。**フォロワーから始め、リーダーは最後**にする
   - パッチ・マイナー更新または最新への更新: `sudo apt-get update && sudo apt-get upgrade`（または `sudo apt-get install db-branch db-branch-<モジュール>`）
   - 版を指定するとき: `sudo apt-get install db-branch=<版> db-branch-<モジュール>=<版>`
3. コアと一緒にモジュール（`db-branch-proxysql` など）も上がった場合、まだ更新していないノードに影響を与えないよう、各ノードのエージェントはクラスターの記録より新しいモジュールをダウングレードせず維持する（警告と `module.version_ahead` イベント、`dbbranch_module_problem` メトリクスが出る）。全ノードを上げ終えたあと、クラスターの記録を合わせるには任意のノードで次を実行する:
   ```sh
   db-branch module install <モジュール名> --version <新しい版>
   ```
   （最新候補と一致していれば `--version` は省略可）
4. 各ノードで `db-branch update status` と `db-branch module list` を見て、全ノードが同じ版になり、モジュールが揃っていることを確かめる

## API

`GET /v1/updates`（`update.read`）、`POST /v1/updates/check`（`update.check`）、`POST /v1/updates` `{"target": "<版>"}`（`update.apply`、202）、`DELETE /v1/updates`（`update.apply`）。詳細は [api.md](api.md) §5.4.1。

## Raft の互換性

コマンド `put_update_check`・`start_rollout`・`record_rollout` はプロトコル 12 で加わった。全ノードが 12 になるまで書かれない。
