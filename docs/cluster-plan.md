## C1. 状態の複製とメンバー管理

- `hashicorp/raft` + `raft-boltdb` を agent に組み込む。リーダーは自動選出
- FSM の状態: ベース、ブランチ、ノード、参加トークンのハッシュ・有効期限
- `domain.Store` の Raft 実装。読み取りは手元の状態、書き込みはリーダーで Apply（フォロワーはノード間 API でリーダーへ転送）
- `db-branch cluster init`: クラスタ CA を作り、1 台構成で bootstrap。単一ノードの state.json があれば取り込む
- `db-branch cluster token [--ttl <duration>]`: 1 回限り・有効期限付き（既定は設定 `cluster.join_token_ttl` の `24h`）の参加トークン（CA 証明書の SHA-256 + 秘密値）を発行。`POST /internal/v1/join` で CA を渡した時点で Raft ログ（`consume_join_secret`、Protocol 27）上で即座に消費され、期限切れや 2 回目以降の参加は `403` で拒否される。ローリング更新中の混在クラスタ（Protocol 27 未満）では旧来の `set_join_secret`（Protocol 1）にフォールバックし、参加時の消費も旧コマンドで消去することで参加が止まらない
- `db-branch cluster join <addr> --token T`: CA をトークンのハッシュで検証してから参加。リーダーが非投票者として追加し、下の「投票者の上限と自動入れ替え」に従って昇格する（リーダーが古い版なら従来どおり投票者として追加される）
- `db-branch cluster remove <node> [--force]`: 故障した（または退役する）ノードをクラスタから外す。Raft の構成とノード一覧から消す。API は `DELETE /v1/cluster/nodes/{name}`。リーダーが行い、フォロワーに届いた要求はリーダーへ転送される
  - 投票者を外した結果、残る投票者の健全な数が過半数に満たなくなる削除は `409 conflict` で拒否する（先に別のノードを昇格させるか、故障を直す）。リーダー自身は外せない（別のノードから実行する）
  - そのノードがベースの原本・コピー・ブランチをまだ持っているときは、`--force` なしでは `409 in_use` で拒否し、一覧を示す。`--force` は、それらの**記録**を忘れる（ノード上のデータには触れない）。他のノードのブランチが元にしているベースの原本は、`--force` でも消さない。原本を忘れたベースが他のノードにコピーを残しているときは、そのコピー（データ）は他のノードにそのまま残り、db-branch の管理から外れる（結果の `orphaned` に出る。不要なら各ノードで消す）。他のベースのコピー先一覧（`replica_nodes`）にそのノードの名前があれば、ほかに残るものがなければ `--force` なしでもそこから外す。外されたノードがまだ動いていても、リーダーはその心拍（ノード記録の更新）を受け付けない途中で失敗しても、同じコマンドをもう一度実行できる
- `db-branch cluster leave [--force]`: このノード自身を、他のノードの手を借りずに `cluster remove` する（リーダーでは実行できない）
- 各ノードは 10 秒ごとに自分の情報（アドレス、バージョン、空き容量、メモリ）を書き込む
- `GET /v1/cluster`、`db-branch cluster status`、コンソールの Cluster 画面にノードとリーダーを表示

### 投票者の上限と自動入れ替え

- 全ノードが投票すると、書き込みは全台の過半数を待つ（10 台なら 6 台）。偶数台は奇数台より耐えられる故障が増えない（10 台も 9 台も 4 台）。5 対 5 に分断されると過半数がどちらにもなく、クラスタ全体が書き込めなくなる
- そこで投票するのは奇数台、最大 5 台（1・3・5）に絞る。ほかのノードは非投票者として、ログを受け取りデータの完全なコピーを持つが、選挙にも過半数にも数えない。目標数は「健全なノード数以下で最大の奇数、ただし 5 まで」
- リーダーが 10 秒ごとに `usecase/membership` で判断し、1 回に 1 つだけ変更して、コミットされるのを待つ。ノード数（健全 = 30 秒以内にハートビートがある）から目標を出し、次の順で決める
  1. 2 分以上途絶えた投票者は、30 秒以上健全だった非投票者が代わりに入れるとき（または投票者が多すぎるとき）に降格する
  2. 投票者がノード総数の目標（`min(総数,5)` 以下の最大奇数）より多ければ、途絶えているものから、なければ名前順で後ろのものを降格する。リーダーは降格しない。停電中のノードも総数に数えるので、一時的な障害で投票者は減らない
  3. 投票者が健全数の目標より少なければ、最も長く健全な非投票者（30 秒以上）を昇格する
  どの変更も、変更後の構成で健全な投票者が過半数を下回らないときだけ行う
- 分断時: 過半数側（投票者の過半数を含む側）だけが書き込みを続ける。5 台構成なら 3 台以上の側。投票者を絞っても、分断された少数側が書き込めない性質は変わらないが、10 台で 5 対 5 に割れても、投票者が 5 台なら 3 台を持つ側があれば書き込める
- 既存クラスタの更新: 構成変更は Raft の標準機能で、FSM のコマンドを足さないので `Protocol` は上げない。新しいリーダーになったノードが、既存の全員投票の構成を少しずつ 5 台に絞る。古いノードがリーダーのあいだは、参加は従来どおり投票者になり、自動の入れ替えは行われない
- 表示: `GET /v1/cluster` の各ノードに `voter`、`db-branch cluster status` の VOTING 列、コンソールの Cluster 画面に「投票ノード / 非投票ノード」を出す

## C2. 担当ノードと配置（2026-11-10 完了）

- `Base.Node` / `Branch.Node` を追加。ベースは作ったノード（`--node` で指定可）、ブランチは配置先が担当になる
- 配置は API を受けたノードが決める（`domain.Placement`）。候補はベースのスナップショットを持つノード（C3 まではベースのノードだけ）のうち、稼働中でメモリ予算（物理メモリの 3/4 を `buffer pool + 256MB` で割った数）に余裕があるもの。ブランチ数が少ないノードを優先し、同数なら名前順
  - 当初はリーダーが決める案だったが、名前の予約を Raft の条件付き挿入（`insert_branch` / `insert_base`、重複は `ErrAlreadyExists`）にしたので、どのノードが決めても衝突しない。偏りが出ても次の配置で均される
- ポートはノードごとに割り当てる（同じポート番号が別ノードにあってよい）
- 担当ノードが別なら、API を受けたノードがノード間 API の `/internal/v1/api/` へ要求をそのまま中継する（mTLS。セッション Cookie は渡さない。`X-Db-Branch-Forwarded` で二重転送を防ぐ）。ただしソケット限定の操作（`POST /v1/auth/reset`、`POST /v1/backups/restore`、`POST /v1/cluster/token`）は `/internal/v1/api/` 経由でも `403 socket_only` で拒否する。ベースの操作（スナップショット・起動・停止・削除）も同じ
- usecase 側でも担当外の操作は `ErrOtherNode` で断る。期限切れの削除と再起動後の復旧は自分の担当分だけ
- オペレーションを Raft に記録し、どのノードからでも見える。変更通知（SSE）は各ノードが Raft の適用結果から流す。agent の再起動時に自分が実行中だった操作は失敗扱いにする。終わった操作は新しい 200 件だけ残す
- フォロワーへの書き込みは、自分の FSM に反映されるまで待ってから返す（書いた直後の読み取りで見える）。中継した側も、転送先で始まった操作が自分に届くまで待って 202 を返す
- 各ノードはハートビートでメモリ量とブランチごとの使用量も書き込み、どのノードのコンソールでも全ブランチの使用量を表示する
- 担当ノードのない記録（C1 以前の状態）は、データセットを持つノードが起動時に引き取る（`Service.Adopt`）

### 分かっている制約

- ローリングアップグレード中、古いバージョンのノードは新しいフィールドを知らずに落とす（C2 の展開時に `node` が消えた。全ノード更新後の再起動で引き取り直して回復）。Raft の状態に互換性のない変更を入れるときは、全ノードが新バージョンになるまで新機能を使わない仕組み（クラスタの最小バージョン）が要る
- ランタイムはクラスタ全体で入れる（C4）

## 1 つのノードからの管理（2026-11-10）

- コンソールの admin パスワードはクラスタで 1 つ（Raft の状態に置く）。最初にクラスタモードで起動したノードのパスワードが採用される。この判定は Raft のログの中で行う（`init_admin`）ので、追いついていないノードが上書きすることはない。採用されなかったノードの初期パスワードファイルは削除する
- `db-branch admin reset-password` はエージェント経由でクラスタ全体のパスワードを変える（エージェントが止まっている単一ノードだけ手元のファイルを直接変える）
- どのノードのコンソール・CLI からも、全ノードのベース・ブランチ・エンジンを操作できる。Cluster 画面には各ノードのエンジンを表示し、そのノードへインストールできる

### ローリングアップグレードでの事故と対策

- 新しいコマンド（`set_admin`）を古いリーダーが受け取り、知らないフィールドを落として中身のないコマンドをログに書いた。全ノードがその適用時に nil 参照で落ち、再起動を繰り返した
- 対策 1: FSM は中身の欠けたコマンドをエラーとして扱い、落ちない
- 対策 2: ノード間の転送はコマンドを元のバイト列のまま渡す（途中のノードが知らないフィールドを落とさない）
- 対策 3（クラスタプロトコル、下記）: 全ノードが対応するまで新しいコマンドを使わない

## クラスタプロトコル（2026-11-10）

- バイナリはプロトコル番号（`raftstore.Protocol`、現在 4）を持ち、ハートビートで報告する。報告のないノード（導入前の版）は 1 とみなす
- クラスタのプロトコル = 登録済みの全ノードの最小値（自分の版が上限）。`GET /v1/cluster` の `protocol`、`cluster status` と Cluster 画面に「更新中」を表示する
- Raft のコマンドはそれぞれ必要なプロトコルを持ち（`opProtocol`）、クラスタがそこに達するまでログに書かない（`ErrClusterUpgrading`、API では 503 `cluster_upgrading`）。古いノードが知らないコマンドを受け取ることはない
- 古いノードが自分で書くコマンドは止めない（そのノードが知っているものだけだから）。ローリングアップグレード中も、操作は古いノードに転送されれば動く
- 実機での確認: node1 だけ新版にした状態で node1 に作らせると `put_operation needs cluster protocol 2, the cluster is at 1` で断り、残り 2 台を更新すると自動でプロトコル 4 になって通った
- コマンドを足す・意味を変えるときは `Protocol` を上げ、`opProtocol` に登録する（CLAUDE.md）

## C3. ベーススナップショットの伝搬（2026-11-10 完了）

- ベースのノードで正常停止 → スナップショット → Raft に記録（従来どおり）
- 各ノードは他のノードのベースを `<pool>/db-branch/replicas/<base>` に写す（`Service.Replicate`、30 秒ごとと、ベースの変更を Raft で受けたとき。失敗したら 5 秒後に再試行）
  - コピーがなければ `zfs send -R base@最新`（過去のスナップショットもすべて）、あれば手元にある最新から `zfs send -I @手元の最新 base@最新`（間のスナップショットもまとめて）
  - ストリームはノード間 API の `GET /internal/v1/bases/{name}/stream?from=&to=`（mTLS、メンバーのみ）。送信途中で失敗したら接続を切り、受け側が不完全なストリームを完了と誤らないようにする
  - 受け側は `zfs recv -u -F`。手元のコピーがベースと共通のスナップショットを持たない（同名で作り直されたベースなど）ときは作り直す
- 受け取ったスナップショットは `add_replica` で Raft に記録（`Base.Replicas`、スナップショットごとの保持ノード）。`put_base` は記録を上書きしないので、古い読み取りからの更新で消えない
- 配置の候補は、そのスナップショットの保持ノード（ベースのノード＋コピーを持つノード）。コピーのあるノードではコピーからクローンする
- ベースを削除すると、各ノードは記録のなくなったコピーを消す（ベースの削除はそのベースのブランチがないときだけできるので、コピーに依存するクローンはない）
- コンソールの Bases 画面で、各スナップショットの下にノードごとの四角を出し、保持しているノードを塗る

## C4. ランタイムの配布（2026-11-10 完了）

- 外部（cdn.mysql.com など）から取得するのはリーダーだけ。リーダーはアーティファクト置き場の検証済みのコピーを、ノード間 API の `GET /internal/v1/artifacts/{engine}/{version}?arch=` で配る
- 他のノードはリーダーから受け取り、自分のバイナリに埋め込まれたカタログの SHA-256 とサイズで検証してから展開する（カタログは署名を確認して固定したもの。Raft には値を置かず、各ノードが自分で検証する）
- `runtime install X` は常にクラスタ全体: Raft に「全ノードに入れるランタイム」として記録し（`add_runtime`、プロトコル 5）、各ノードが不足分をオペレーションとして入れる（1 分ごとと、記録を受けたとき。後から参加したノードにも入る）。ノード個別の追加はない（2026-11-10 に廃止。ブランチはどのノードにも置かれ作り直されるため）。それ以前に個別に入れたランタイムは、各ノードの起動時にクラスタ全体のものとして登録する
- `runtime remove X` は記録を消し、全ノードから削除する。そのノードのベースやブランチが使っていれば消さず、ノード名と理由を返す
- 同じ版の同時インストールは、先に終わった方を正とし、もう一方はインストール済みとして終える
- カタログに mysql@9.6.0（x86_64 minimal、MySQL Release Engineering の署名を確認済み）を追加
- 実機での確認: node2 と node3 で cdn.mysql.com を名前解決できなくした状態で、node3 から `runtime install mysql@9.6.0` を実行し、3 台とも入った（上流から取得したのはリーダーの node1 だけ）。9.6.0 のベースとブランチも動いた

## C5. ノード喪失（2026-11-10 完了）

- 30 秒ハートビートのないノードを `down` とし、リーダーがその上のブランチを `lost` にする（理由に最後の応答時刻を残す。削除中のものはそのまま）
- `db-branch branch recreate <name> [--node N]`（コンソールのメニューにも）: 同じスナップショットを持つ別のノードで、同じ名前・ユーザー・パスワード・期限・init SQL のまま作り直す。init SQL はそのために記録に残す。失われたノード上の変更は戻らない（リセット時点に戻る）
- `lost` のブランチはどのノードからでも削除できる。記録を `deleting` にしておき、そのノードが戻ったら片付ける
- 戻ったノードは 10 秒ごとの照合（`Service.Reconcile`）で、自分の `lost` のブランチを起動して `ready` に戻し、他のノードで作り直されたブランチの手元のコピーを止めて消す。記録のないデータセットは消さない（記録がないことはデータが不要な証拠にならない）
- 実機での確認: node3 の VM を停止すると 34 秒で 2 つのブランチが `lost` になり、片方を node1 に作り直した（3 秒、同じパスワードでデータも戻った）。VM を起動すると 26 秒でもう片方が `ready` に戻り、作り直した方の古いコピーは消えた

## C6. ProxySQL によるルーティング（2026-11-10 完了）

- ProxySQL の扱いはモジュール（`db-branch-proxysql` パッケージが `/usr/lib/db-branch/modules/proxysql` に置く。`ext.Router` を実装）。モジュールがあるときだけ、agent は Raft の状態から振り分けの設定を作り（`routing.Plan`）、変わったときだけモジュールに渡す（5 秒ごとに確認）。モジュールが ProxySQL の管理インターフェースで入れ替えて `LOAD ... TO RUNTIME` / `SAVE ... TO DISK` する。モジュールがなければ agent は ProxySQL に触れない
- 初回は既定の管理資格情報（admin:admin、全インターフェースで待ち受け）を乗っ取り、ランダムなパスワードに替えて `/var/lib/db-branch/proxysql/admin.json`（0600）に保存、管理インターフェースを 127.0.0.1 だけにする。バックエンドの監視は止める（各ブランチに監視用ユーザーが要るため）
- ブランチ 1 つ = hostgroup 1 つ。ID はブランチ名の CRC-32 から決まる（他のブランチの増減で変わらない。偶然の衝突は名前順で次の空き）。サーバーは配置ノードの IP とブランチのポート
- ユーザー名による指定: ブランチのユーザーをブランチ名にした（従来の共通ユーザー `branch` のブランチには、再起動時に同じパスワードでブランチ名のユーザーを足す）。`mysql -u feature-x -h <どのノードでも> -P 6033`
- コメントによる指定: `db-branch route user add app --default main`（パスワードは標準入力）で、全ブランチ共通のユーザー（ベースのダンプにあるアプリのユーザーなど）を登録する（Raft、プロトコル 6）。`/*db_branch='x'*/` でブランチを選び、コメントがなければ既定のブランチ。存在しない名前はエラー（黙って既定へ流さない）。トランザクションの途中ではブランチを変えない
- `db-branch branch dsn x --proxy`、コンソールの「Copy proxy URL」でプロキシ経由の接続 URL を得る
- ProxySQL 3.0.12（公式の ubuntu24 パッケージ、GitHub の SHA-256 を確認）を検証 VM に入れて確認。.deb は `Suggests: proxysql`。同梱（db-branch-proxysql）は配布の段階で行う
- 実機での確認: どのノードの 6033 からでも、ユーザー名で 3 台に散らばったブランチへ届いた。共通ユーザーでコメントにより node1 と node2 のブランチを切り替え、未知の名前はエラー、トランザクション中は切り替わらなかった。新しいブランチは作成から 2 秒でプロキシ経由で届き、削除すると届かなくなった
- PostgreSQL（pgsql_*）は PostgreSQL エンジンの実装と合わせて行う
